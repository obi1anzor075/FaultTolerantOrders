# Transactional Outbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Сохранить событие заказа при сбое API и восстановить публикацию после перезапуска.

**Architecture:** API сохраняет заказ и Outbox одной транзакцией. Scoped dispatcher выбирает сообщение с PostgreSQL row lock; BackgroundService вызывает его периодически. Publisher confirms предшествуют записи PublishedAt.

**Tech Stack:** .NET 10, EF Core, PostgreSQL, RabbitMQ.Client 7.2.2, xUnit; SQLite только для локальных storage-тестов.

**Spec:** `docs/outbox-design.md`, согласованный в чате этап Transactional Outbox.

## Global Constraints

- Существующие заказы и журнал baseline сохраняются.
- HTTP Idempotency и Inbox не добавляются на этом этапе.
- Повтор сохраняет MessageId; exactly-once delivery не заявляется.
- Poll interval: 2 секунды; batch size: 20; publish timeout: 10 секунд; retry delay: 1–30 секунд.
- Docker локально недоступен; это явно ограничивает подтверждённые результаты.

## Review Focus

- Ошибка INSERT Outbox: не должно остаться заказа без события.
- Брокер недоступен: событие должно остаться pending с отложенным retry.
- Confirm ещё не получен: PublishedAt должен оставаться пустым.
- Несколько экземпляров: в PostgreSQL строка выбирается единственным dispatcher.
- Existing baseline DB: миграция не должна удалить старые заказы.
