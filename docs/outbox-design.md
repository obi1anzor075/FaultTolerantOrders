# Transactional Outbox: решение для второго этапа

Цель: после сбоя API между сохранением заказа и отправкой события сохранить возможность доставки. HTTP Idempotency и Inbox остаются отдельными следующими этапами.

## Сохранение

`OrderWriter.CreateAsync` создаёт Order, OrderItems и OutboxMessage, затем вызывает один SaveChangesAsync. Для PostgreSQL это одна локальная транзакция. Id записи Outbox одновременно является MessageId события и не меняется при повторных попытках. Ответ 201 означает, что заказ и событие сохранены; уведомление обрабатывается асинхронно.

OutboxMessage: Id, OrderId, Type, Payload (jsonb), OccurredAt, PublishedAt, RetryCount, NextRetryAt, Error. Внешний ключ связывает событие с заказом; уникальная пара OrderId/Type запрещает повторную запись OrderCreated для одного заказа.

## Публикация

BackgroundService получает scoped-диспетчер. Диспетчер открывает транзакцию и выбирает одно готовое сообщение через FOR UPDATE SKIP LOCKED. Блокировка строки сохраняется на время публикации и фиксации результата, чтобы параллельные экземпляры не публиковали эту строку одновременно. Время сетевой операции ограничено 10 секундами. Этот простой подход расходует соединение с БД во время отправки; оптимизация через lease остаётся за пределами этапа.

RabbitPublisher использует publisher confirms и mandatory=true. PublishedAt записывается только после подтверждения. При ошибке сохраняются RetryCount, Error и время следующей попытки; задержка растёт от 1 до 30 секунд. После аварийного завершения транзакция и блокировка снимаются, незавершённое событие остаётся доступным.

Если брокер принял событие, но процесс упал до фиксации PublishedAt, возможна повторная отправка с прежним MessageId. Exactly-once delivery не заявляется. Consumer пока способен создавать повторные Notifications; это будет решаться Inbox.

Ожидание публикации ограничено также на уровне диспетчера доставки через WaitAsync: если клиент продолжает закрывать канал после отмены, приложение наблюдает его eventual error отдельно и освобождает транзакцию после сохранения retry. Результат публикации при таймауте неопределённый, поэтому позднее завершение может привести к повтору. Ограничение 10 секунд относится к ожиданию публикации, не к SQL-операциям или полной готовности системы.

## Схема и эксперимент

OrderService переходит на миграции EF Core. Начальная миграция допускает существующие таблицы строго известной baseline-схемы (Orders и OrderItems) и добавляет Outbox без удаления старых заказов. События для исторических заказов автоматически не создаются. NotificationService остаётся с прежней схемой.

Откат начальной миграции удаляет только OutboxMessages, сохраняя Orders и OrderItems, в том числе ранее существовавшие. Это переход к baseline-схеме; данные Outbox при таком откате не сохраняются.

Чтобы фоновый процессор не успел обработать событие до инъекции падения, отдельный Compose override отключает его на подготовительном этапе опыта. После проверки pending-записи override снимается и процессор доставляет сохранённое событие. Это фиксируется в методике как управляемая пауза публикации.

## Проверка

SQLite-тесты проверяют атомарное сохранение при ошибке INSERT Outbox, сохранённый JSON, ожидание подтверждения и устойчивый MessageId при ошибке/повторе. Они не проверяют PostgreSQL-блокировки. Отдельные PostgreSQL-тесты по OUTBOX_TEST_POSTGRES проверяют миграцию старой схемы и SKIP LOCKED; каждый тест использует свою временную схему. Полный опыт RabbitMQ выполняется на компьютере пользователя с Docker, результаты заносятся только после выполнения.
